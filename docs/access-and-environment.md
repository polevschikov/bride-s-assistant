## Аккаунты администраторов и клиентов

- Администратор один, вход по `ADMIN_ACCESS_CODE` на `/?admin=1`. Отдельного имени пользователя и ролевой модели нет.
- Admin bearer-токены выпускаются при входе, живут 7 дней в памяти Node.js и исчезают при перезапуске.
- Клиенты создаются демонстрационно на `/?account=1`; постоянных паролей нет. Их bearer-сессии хранятся в таблице `client_sessions` до 30 дней.
- Внешних сервисных аккаунтов агент не создавал.

## Выданные или затронутые агентом доступы

1. `ADMIN_ACCESS_CODE` — сгенерирован агентом 6 ноября 2026 для админки. Владельцу следует перевыпустить при передаче проекта.
2. `SANDBOX_SECRET` — ранее сгенерированная серверная HMAC-строка для sandbox. Перевыпустить при передаче, если sandbox продолжает использоваться.
3. Пароль `root` к VPS — предоставлен владельцем в чате, не создан агентом; перевыпустить из-за передачи в переписке.
4. Пароль DNS-панели — предоставлен владельцем в чате, не создан агентом; перевыпустить из-за передачи в переписке.
5. Демонстрационные admin/client bearer-токены — временные; не передавать новому агенту. Административные удаляются перезапуском, клиентские можно отозвать удалением строк `client_sessions` по отдельной задаче.

GitHub PAT, OAuth secrets, S3 keys, ЮKassa keys, SMTP/API keys и другие сервисные токены агент **не создавал и не выпускал**.

## Порядок ротации владельцем, не исполнять автоматически

1. Сохранить выведенные отдельно значения в менеджер паролей.
2. Перевыпустить root и DNS-пароли в панелях REG.RU.
3. Заменить `ADMIN_ACCESS_CODE` в `workspace.conf`, выполнить `systemctl daemon-reload && systemctl restart bride-assistant` и проверить вход.
4. Заменить `SANDBOX_SECRET` в окружении systemd и перезапустить службу. Старые неподтверждённые sandbox-ссылки перестанут проходить подпись.
5. Проверить сайт и админку. Только после подтверждения владельца удалить секреты из доступных ему локальных заметок; историю чата агент сам изменить не может.

# Передача проекта новому агенту

## Порядок чтения

1. `AGENTS.md`, `docs/STATUS.md`, `docs/conventions.md` — актуальные инструкции и состояние.
2. При продолжении — `docs/tasks/<задача>.md` и фактический git status/diff.
3. Только нужные разделы `docs/project-map.md`, затем соответствующие исходники и требования. По изменению поведения — `docs/decisions.md`, `docs/PRODUCT_PLAN.md` и актуальные источники владельца.
4. По типу задачи: `docs/workflow.md` (ветки и ход работы), `docs/testing.md` (проверки), `docs/recovery.md` (сбой), `docs/releases.md` (версии).
5. `docs/architecture.md`, `docs/setup.md`, `docs/known-issues.md`, `docs/access-and-environment.md` читать адресно при необходимости. Весь docs/ каждый раз не перечитывать.

## Состояние проекта

«Ассистент невесты» — работающий прототип на единственном стенде REG.RU: React + TypeScript + Vite, Express и SQLite. Публичный сайт, квизы A/B, планер, sandbox-оплата, админка, CMS, медиабиблиотека и демонстрационный личный кабинет опубликованы по IP без домена и HTTPS. Основной код релиза — `c832e72`, проверенный статус — `1698a1e`. Это не боевой запуск: OAuth, реальные платежи, S3 и роли не подключены.

## Что делать первым

Если владелец уже дал задачу, самостоятельно выполнять её по AGENTS.md и docs/workflow.md. Если задачи нет, кратко сообщить понимание и ждать поручение. Настройка автономного локального процесса разрешена владельцем 08.11.2026; рабочий сайт и сервер трогать запрещено. Раннее требование сначала выдать резюме передачи не должно останавливать выполнение уже данного поручения.

Секреты находятся вне Git. Их расположение описано в `docs/access-and-environment.md`; запрашивать или использовать их нужно только в рамках отдельной задачи владельца.

## Контракт работы нового агента

1. Канон текущих правил — AGENTS.md и conventions.md; поручение владельца имеет приоритет. Исходные продуктовые материалы сохраняются.
2. Читай связанные функции и их контекст достаточно для безопасного изменения; не загружай весь проект без необходимости.
3. Обновляй затронутую документацию и сохраняй состояние существенной задачи. Не переписывай неизменившиеся документы ради формальности.
4. Технические противоречия проверяй самостоятельно по коду, тестам, истории и фактическому состоянию; исправляй документ с основанием. Если расходятся продуктовые решения либо неизвестны полномочия, уточни конкретный выбор у владельца.
5. Владелец не обязан диагностировать сбой. Сообщай обычным языком результат, подтверждение и ограничения; не выдавай гипотезу за причину.
6. Продолжай все независимые разрешённые части работы; не начинай новые продуктовые задачи без поручения.

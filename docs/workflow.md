# Работа, ветки и версии

Основание: поручение владельца 08.11.2026 о локальной настройке автономности. Сохраняются продуктовые решения и ограничения conventions.md. Практики диагностики и release из standarts перечислены в process-audit.md; адаптация не требует установки пакета или команды субагентов.

## Одна задача

1. По поручению установить критерии и допустимые изменения. Проверить git status, текущую ветку и исходный commit; сохранять чужую работу.
2. Если уже находишься в подходящей ветке задачи, продолжить её. Иначе создать `feat/<смысл>`, `fix/<смысл>` или `chore/<смысл>` от проверенной базы. `main` — интеграционная ветка, не место незаконченного эксперимента. Команды выполнять из корня app/.
3. Сначала адресное чтение карты и состояния. Для бага — recovery.md; для бизнес-логики — источники требований; для дизайна — актуальные макеты и принятые ограничения. Не расширять MVP технической инициативой.
4. Выполнить небольшое изменение. Проверить сценарий и связанные риски. Для кода перед локальным финальным коммитом — `npm run check`. Для документации без изменения поведения достаточно проверки ссылок и согласованности; не запускать всё повторно без причины. Известный lint-долг не выдавать за исправленный, новые проблемы в затронутой зоне не скрывать.
5. Просмотреть полный diff от базы, staged/unstaged/untracked, убрать только собственные случайные правки. `git diff --check`. Сделать локальный коммит по одной задаче с понятным английским именем. Не включать секреты, БД, node_modules, результаты тестов. Незавершённое допускается сохранить локальным WIP-коммитом, явно без статуса готовности.
6. Заполнить состояние задачи по шаблону ниже и обновить только изменившиеся части карты/решений/ограничений. Не копировать весь лог.
7. При отдельном поручении отправки — push рабочей ветки и PR в main. CI должен пройти; проверить результат по факту. Защита main уже включена: PR и успешный `check` от GitHub Actions (app_id 15368), актуальная база, закрытые обсуждения; правила действуют также для администратора. Force-push и удаление запрещены; внешнее одобрение не обязательно. При изменении настроек проверять их через API, наличие YAML само не подтверждает защиту. Слияние и выкладка — разные действия с отдельными основаниями.

## Выпуск

Каждый фактический выпуск: версия `v0.MINOR.PATCH` → точный commit → окружение → время → проверки → предыдущая совместимая версия → данные/конфигурация/backup → способ отката. Пока это прототип, новые функции повышают MINOR, исправления PATCH. Начальный номер выбрать при первом подтверждённом выпуске; существующий сервер задним числом не тегировать как проверенный.

После принятия и разрешения выпуска поставить аннотированный тег на точный commit, записать releases.md. Деплоить именно проверенную ревизию, а не произвольную вершину main. Теги не передвигать; следующий выпуск получает новый тег. Push коммита или тега не должен сам менять сервер. Возврат опубликованного изменения — отдельный revert с проверками; не переписывать общую историю reset/force-push.

## Состояние задачи

Создать `docs/tasks/<краткое-имя>.md` при существенной работе:
- Цель, критерии, границы; решения владельца.
- Ветка, исходный commit, изменённые зоны, источники/версии.
- Симптом и наблюдения; проверенные и опровергнутые гипотезы.
- Что сделано; команды и результаты с датой/окружением, путь к локальным диагностическим артефактам.
- Что не проверено, препятствия, остаток, один следующий шаг.
- Локально/отправлено/слито/развёрнуто — отдельно, со ссылками при наличии.

При продолжении сверить состояние с git status/diff и актуальными источниками. Имя ветки/тега из документа не является доказательством текущего состояния.
